= Karate API Testing Demo

A hands-on demo of link:https://github.com/karatelabs/karate[Karate] for API testing, built to
be run end-to-end with nothing to install beyond a JDK and Maven. It covers:

. *Configuration through parameters* - environment-driven config (`karate-config.js` +
  `-Dkarate.env`) and data-driven scenarios (`Scenario Outline` + `Examples`).
. *Use-case (functional) testing* - a full CRUD lifecycle against a REST API.
. *Load testing* - the _same_ feature files reused as a Gatling load test, Karate's
  headline benefit over hand-rolling a separate performance test suite.
. *CI automation* - two GitHub Actions workflows, one automatic and one on-demand.

There is no external API and nothing to deploy: the "API under test" is itself a Karate
feature file (`src/test/java/mock/users-api.feature`), started as a
link:https://docs.karatelabs.io/extensions/test-doubles/[Karate MockServer] - a small
in-memory, non-persistent CRUD service for a "users" resource. This also doubles as a second
demonstration of Karate's range: it can act as an HTTP _client_ (the tests) and an HTTP
_server_ (the mock) at the same time.

For the `make` targets, the mock runs as a local Docker image (built from the bundled
`Dockerfile`, started via `docker-compose.yml`) so both the functional tests and the load test
exercise the exact same containerized service on a fixed port.

== Prerequisites

* JDK 17 (Karate 1.4.x does not run on JDK 22+)
* Maven 3.9+
* Docker (or a compatible `docker compose`, e.g. Podman) - only needed for the `make` targets
  below; running `mvn test` directly falls back to an in-process mock (see below)
* GNU Make (optional - a thin wrapper around the commands below, to make the demo easier to
  drive)

== Quickstart

[source,shell]
----
make demo    # functional tests, then the load test, end to end
make help    # list all available targets
----

[cols="1,3"]
|===
| Target | What it does

| `test` / `test-dev`
| Build+start the mock via Docker Compose, run the functional tests (`karate.env=dev`), stop the mock

| `test-ci`
| Same, with `karate.env=ci`

| `mock-start`
| Build (if needed) and start the mock API container, wait until healthy

| `mock-stop`
| Stop the mock API container

| `load-test`
| `mock-start`, run the Gatling load test, `mock-stop` - always, even on failure

| `demo`
| `test-ci` then `load-test`

| `clean`
| `mvn clean`, plus stop/remove any lingering mock API container
|===

== Project layout

----
Dockerfile                      # builds the mock API image (mvn + the test classpath, runs MockServerMain)
docker-compose.yml               # runs that image on a fixed port, with a healthcheck
Makefile
scripts/
  mock-start.sh                 # docker compose up --build --wait
  mock-stop.sh                   # docker compose down
  functional-test.sh             # mock-start -> mvn test -Dmock.server.url=... -> mock-stop
  load-test.sh                   # mock-start -> mvn gatling:test -> mock-stop, cleans up on failure too
pom.xml
src/test/java/
  karate-config.js           # environment-driven config
  logback-test.xml
  mock/users-api.feature      # the bundled demo API (in-memory CRUD mock)
  support/
    MockServerLifecycle.java  # starts/stops the mock once per functional test run, unless an
                               # external mock.server.url (the Docker container) is already set
    MockServerMain.java       # runs the mock standalone, for the load test / Docker image
  demo/users/
    create-user.feature       # @ignore'd helper, reused via `call` from other features
    users-create.feature       # create: happy path + data-driven validation (Examples)
    users-read.feature         # read: get by id, not-found, list
    users-update.feature       # update
    users-delete.feature       # delete + confirm gone
    fixtures/invalid-user.json # example payload fixture, read() from an Examples row
src/test/scala/perf/
  UsersSimulation.scala        # Gatling simulation that replays the create/read features
.github/workflows/
  functional-tests.yml         # runs on push/PR
  load-test.yml                # manual (workflow_dispatch)
----

== Running the functional tests

[source,shell]
----
make test          # builds/starts the mock via Docker Compose, runs karate.env=dev, stops the mock
make test-ci        # same, with karate.env=ci
----

This starts the mock API as a Docker container on a fixed port (see `docker-compose.yml`) and
runs every `*.feature` file under `demo/users` against it. Reports are written to
`target/karate-reports/` (open `karate-summary.html`) and `target/surefire-reports/`.

Running `mvn test -Dkarate.env=dev` directly (no Docker) still works: `MockServerLifecycle`
only reuses an external mock when `mock.server.url` is already set, and otherwise falls back
to starting one in-process on a random free port, same as before. This is what the
`functional-tests.yml` CI workflow does.

=== Configuration through parameters

`karate-config.js` branches on `karate.env` (default `dev`) to vary timeouts per environment -
`test` and `test-ci` above are just the `mvn test -Dkarate.env=...` command for each:

[source,shell]
----
mvn test -Dkarate.env=ci     # longer read timeout, for slower CI runners
mvn test -Dkarate.env=dev    # local defaults
----

In a project pointed at a real service, this is also where you'd switch `baseUrl` between
dev/qa/prod hosts. Since this demo's API is bundled, `baseUrl` instead comes from a system
property (`mock.server.url`) that's injected at runtime with whichever port the mock server
happens to be using - another form of "configuration through parameters", just wired
programmatically instead of via `-D`.

`users-create.feature` also demonstrates data-driven parameterization _within_ a feature: a
`Scenario Outline` replays the same validation check against four different payloads via an
`Examples` table, including one read from an external fixture file
(`fixtures/invalid-user.json`).

== Running the load test

Gatling runs in a separate JVM process from the functional tests, so the mock API needs to be
running standalone first, on a fixed port. The `load-test` target takes care of starting it,
waiting until it's ready, running Gatling, and stopping it again - including if Gatling fails:

[source,shell]
----
make load-test
make load-test GATLING_USERS=50 GATLING_RAMP_SECONDS=20   # override the load profile
----

Open the HTML report path Gatling prints at the end (under `target/gatling/`).

Equivalently, across two terminals (useful if you want to inspect the mock API's state, e.g.
with `curl`, while a load test runs against it):

[source,shell]
----
# terminal 1 - build and start the mock API container, leave it running
make mock-start
# (equivalent to: docker compose up -d --build --wait)

# terminal 2 - run the load test against it
mvn test-compile gatling:test -Dgatling.users=50 -Dgatling.rampSeconds=20

# afterwards
make mock-stop
----

`UsersSimulation.scala` replays the exact same `users-create.feature` and `users-read.feature`
scenarios used by the functional suite (selected by a `@name=...` tag) under a ramping load
profile - there is no separate load-test scripting of the API calls themselves.

== GitHub Actions

* *`functional-tests.yml`* runs on every push/PR to `main`/`develop`: `mvn test -Dkarate.env=ci`,
  publishing a rendered test summary on the PR and uploading the Karate/Surefire reports as
  build artifacts, even on failure.
* *`load-test.yml`* is manual (`workflow_dispatch`, with `users`/`rampSeconds` inputs): it
  starts the mock API in the background, waits for it to respond, runs the Gatling
  simulation, stops the mock API, and uploads the Gatling HTML report as a build artifact.

== Adapting this to a real API

Swapping the bundled mock for a real service mainly touches `karate-config.js`: replace the
`mock.server.url`-derived `baseUrl` with real per-environment URLs, and drop
`MockServerLifecycle`/`MockServerMain`, the `mock/` feature, and the `Dockerfile`/
`docker-compose.yml`. Everything else - the CRUD feature files, the reusable `call`-based
helper, the Scenario Outline, the Gatling simulation and both workflows - carries over
unchanged, since none of it actually depends on the API under test being a mock.
